INCONSISTENCIA #1: OPERACIÓN 2 - AMORTIZACIÓN AEE
===============================================================================

ARCHIVO PHP: src/Services/AmortizacionCalculadora.php
ARCHIVO JAVA: legacy/CrearCajaAction.java (líneas 1287-1532)

PROBLEMA CRÍTICO: Cálculo de gastos administrativos cuando montoA <= ga

CÓDIGO LEGACY JAVA (líneas 1371-1376):
----------------------------------------
else{
    // sobregiro gastos administratvos
    gami = Double.parseDouble(ga) - montoA;      
    (ga) = String.valueOf(montoA);
    montoA = 0;
}

CÓDIGO PHP (líneas 99-103):
---------------------------
else {
    $gami = $ga - $montoA;
    $ga = $montoA;
    $montoA = 0;
}

INCONSISTENCIA:
---------------
En el código Java, cuando el monto pagado es menor que los gastos administrativos,
se asigna el valor de montoA a la variable ga (que es un String en Java).
En PHP, se hace lo mismo, pero esta asignación NO se refleja en el movimiento
final guardado en f15_movimiento.

En el legacy Java (línea 1461):
    mov.setGastosa(String.valueOf(ga));

En PHP (línea 208):
    'gastosa' => $ga,

El problema es que en PHP, $ga mantiene su valor original del formulario,
no el valor ajustado cuando hay sobregiro de gastos administrativos.

IMPACTO:
--------
- Cuando el pago es insuficiente para cubrir gastos administrativos, el
  movimiento en f15_movimiento registra el valor original de gastos
  administrativos en lugar del monto realmente pagado.
- Esto causa que el monto del movimiento sea incorrecto.
- Los saldos de gastos pendientes (f16_gastosa) pueden no coincidir con
  los movimientos registrados.

SOLUCIÓN RECOMENDADA:
--------------------
En AmortizacionCalculadora.php, línea 208, cambiar:
    'gastosa' => $ga,

Por:
    'gastosa' => $ga_original_ajustado,

Donde $ga_original_ajustado debe ser el valor de $ga después de la lógica
de sobregiro (línea 101 del código PHP actual).

PROBLEMA: Cálculo de saldo cuando sobregiro < 0 (exceso de pago)

CÓDIGO LEGACY JAVA (líneas 1500-1507):
----------------------------------------
if(sobregiro < 0) {
    //  amortiza = new Double(co2.getAmortizacion());
    sobregiro = -sobregiro;
    r = (new Double(saldo) -  new Double(co2.getAmortizacion())) - sobregiro;

    //   amortiza = new Double(co2.getAmortizacion());
    //   r=   new Double(co2.getResto()) ;
}

CÓDIGO PHP (líneas 179-185):
-----------------------------
if ($sobregiro < 0) {
    // Cuando hay exceso de pago (sobregiro negativo), el legacy
    // RESTA el sobregiro negativo del saldo (líneas 1500-1507)
    $sobregiro = -$sobregiro;
    $r = ($saldo - $amortizacion) - $sobregiro;
    $amortizapAportacion = -$sobregiro; // Sobregiro negativo (exceso)

INCONSISTENCIA:
---------------
El código PHP está correcto en el cálculo del saldo, pero hay un problema
en la asignación de $amortizapAportacion. En el legacy Java, cuando hay
sobregiro negativo (exceso de pago), NO se actualiza el campo de aportación
del préstamo en esta sección del código.

El legacy Java solo actualiza la aportación en los casos:
- Líneas 1312, 1322, 1331: Cuando hay sobregiro positivo
- Líneas 1488-1496: Cuando hay sobregiro positivo y se ajusta

En PHP, se está asignando $amortizapAportacion = -$sobregiro (línea 184),
lo cual podría causar que se actualice incorrectamente el campo f16_sobre
cuando hay exceso de pago.

IMPACTO:
--------
- Cuando un cliente paga más de la cuota, el sistema PHP podría estar
  registrando incorrectamente un sobregiro negativo en el préstamo.
- Esto afecta el cálculo de futuros pagos y el estado del préstamo.

SOLUCIÓN RECOMENDADA:
--------------------
En AmortizacionCalculadora.php, línea 184, cambiar:
    $amortizapAportacion = -$sobregiro;

Por:
    $amortizapAportacion = 0; // No actualizar aportación cuando hay exceso

O eliminar completamente la asignación en el caso de sobregiro < 0.

PROBLEMA: Fuente del monto de aporte COPE

CÓDIGO LEGACY JAVA (líneas 1659-1668):
----------------------------------------
if(bean!=null){
    int de=     new Integer( bean.getAporteCope());
    
    int todiato = 0;
    
    todiato = new Integer(de);

    // aporta = new Double(todiato);

CÓDIGO PHP (líneas 56-60):
---------------------------

$montoAporteCope = $this->obtenerMontoAporteCope($this->pdo, trim($datos['cliente']));

INCONSISTENCIA:
---------------
En el código Java, se obtiene el aporte COPE del socio (bean.getAporteCope())

  del monto de aporte COPE por período.

   ingresar el monto manualmente (similar a 'apeno' en Java)
2. Si existe, agregar lógica para usar ese valor si está presente
3. Si no existe, confirmar que el comportamiento de PHP es correcto
   (usar siempre el valor configurado en el socio)

INCONSISTENCIA #5: OPERACIÓN 10 - PAGO DE SOBREGIRO DE PRÉSTAMO
===============================================================================

ARCHIVO PHP: src/Services/SobregiroPrestamoServicio.php
ARCHIVO JAVA: legacy/CrearCajaAction.java (líneas 1901-2099)

PrestamoBean b2 = getCreditos().getPrestamo(new Integer(crearform.getChk()));

double m = 0;

CÓDIGO PHP (líneas 119-129):
----------------------------
// Calcular sobregiros reales basados en el préstamo
$gastosaPrestamo = (float) ($prestamo['f16_gastosa'] ?? 0);
$moraPrestamo = (float) ($prestamo['f16_gastosm'] ?? 0);

INCONSISTENCIA:
---------------
En el código Java, primero se calcula gami y gamo basado en la distribución
del monto pagado (líneas 1926-1977), y LUEGO se sobrescribe con el cálculo
basado en el préstamo (líneas 2033-2039).

En PHP, se hace el cálculo basado en el préstamo (líneas 119-129) pero
se ignora el cálculo previo de distribución del monto (líneas 76-117).

El problema es que en PHP, las líneas 76-117 calculan valores que luego
son completamente ignorados por las líneas 119-129.

IMPACTO:
--------
- El cálculo de distribución del monto pagado en PHP no se usa realmente.
- Los valores de gastos pendientes (gami, gamo) se calculan incorrectamente
  si el préstamo tiene valores diferentes a los del formulario.
- Esto puede causar que se actualicen incorrectamente los campos
  f16_gastosa y f16_gastosm del préstamo.

SOLUCIÓN RECOMENDADA:
--------------------
1. Analizar si el cálculo de distribución (líneas 76-117) es necesario
2. Si es necesario, combinar ambos cálculos de forma similar al legacy:
   - Primero calcular distribución del monto pagado
   - Luego ajustar basado en los valores actuales del préstamo
3. Si no es necesario, eliminar el código de distribución (líneas 76-117)
   para evitar confusión

INCONSISTENCIA #6: OPERACIÓN 10 - PAGO DE SOBREGIRO DE PRÉSTAMO
===============================================================================

PROBLEMA: Actualización de saldo con amortización

CÓDIGO LEGACY JAVA (líneas 2081-2086):
---------------------------------------
if(amortiza > 0) {
    double saldroPres = Double.parseDouble( b.getSaldo());
    double resto = saldroPres - amortiza;
    amortizap.setSaldo(String.valueOf(resto));  
    getCreditos().actualizarSaldoSolo(amortizap);
}

CÓDIGO PHP (líneas 149-153):
-----------------------------
// Actualizar saldo si hay amortización
if ($amortizacion > 0) {
    $saldoPrestamo = (float) ($prestamo['f16_saldo'] ?? 0);
    $nuevoSaldo = max(0, $saldoPrestamo - $amortizacion);
    $this->actualizarSaldoSolo($this->pdo, (int) $prestamoCodigo, $nuevoSaldo);

INCONSISTENCIA:
---------------
El código PHP usa max(0, ...) para evitar saldos negativos. El código Java
NO tiene esta protección, permitiendo saldos negativos si la amortización
es mayor al saldo.

IMPACTO:
--------
- Si la amortización excede el saldo del préstamo, PHP lo dejará en 0,
  mientras que Java lo dejaría negativo.
- Esto puede causar diferencias en reportes de saldos y estados de préstamos.
- Es necesario verificar cuál es el comportamiento deseado según las
  reglas del negocio.

SOLUCIÓN RECOMENDADA:
--------------------
1. Verificar con la clienta si los saldos negativos están permitidos
2. Si NO están permitidos, mantener el max(0, ...) en PHP
3. Si SÍ están permitidos, eliminar el max(0, ...) para coincidir con Java
4. Documentar la decisión tomada

INCONSISTENCIA #8: GENERACIÓN DE CÓDIGOS DE MOVIMIENTO
===============================================================================

PROBLEMA: Diferentes métodos de generación de ID

CÓDIGO LEGACY JAVA:
-------------------
Usa MAX(f15_codigo) + 1 sin bloqueo explícito FOR UPDATE en la mayoría
de casos (condición de carrera posible).

CÓDIGO PHP:
------------
Usa MAX(f15_codigo) + 1 con FOR UPDATE en todas las operaciones.

INCONSISTENCIA:
---------------
El código PHP es MÁS SEGURO que el legacy Java al usar FOR UPDATE.
Sin embargo, esto es una mejora, no una inconsistencia funcional.

IMPACTO:
--------
- Ningún impacto negativo. El código PHP previene condiciones de carrera
  que el código Java podría tener.
- Los códigos generados pueden ser diferentes si hay concurrencia, pero
  esto es un comportamiento correcto.

SOLUCIÓN RECOMENDADA:
--------------------
MANTENER la implementación actual con FOR UPDATE. Es una mejora de
seguridad sobre el legacy.
